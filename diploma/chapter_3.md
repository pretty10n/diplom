# Глава 3. Разработка и реализация системы автоматизированного заполнения документов

## 3.1 Обоснование инструментальных средств разработки системы

Выбор технологического стека определялся требованиями к надёжности серверных расчётов, зрелости экосистемы и возможности интеграции с форматом Excel. Для серверной части выбран Java 21 и Spring Boot 3.3.5. Java обеспечивает строгую типизацию, что снижает риск ошибок при работе с BigDecimal в финансовых расчётах; Spring Boot предоставляет готовую инфраструктуру для REST API, JPA, валидации и тестирования, сокращая объём шаблонного кода.

Spring Data JPA выбран для доступа к PostgreSQL, поскольку доменная модель содержит устойчивые сущности (Document, DocumentEntry, ReferenceMaterial, ReferenceSupplier, справочники разделов) и отношения один-ко-многим. Flyway использован для версионирования схемы БД: миграция V1 создаёт базовую модель, V2 деактивирует исключённые разделы, V3 добавляет таблицы reference_supplier и reference_material с индексами для поиска и ограничениями уникальности. Такой подход обеспечивает воспроизводимость окружения при развёртывании на стендах разработки и приёмки.

PostgreSQL 15 выбран как промышленная СУБД с поддержкой JSONB, ограничений CHECK и GIN-индексов. Хранение полей строки в JSONB позволяет эволюционировать каноническую модель без частых DDL-изменений, что важно на этапе уточнения маппинга граф форм.

Для клиентской части применены React 18 и TypeScript 5.6. React обеспечивает компонентную модель, удобную для пошагового мастера с локальным состоянием и условным рендерингом полей. TypeScript повышает надёжность интеграции с API за счёт статической типизации DTO. Сборщик Vite 5.4 ускоряет цикл разработки и предоставляет проксирование /api на backend в dev-режиме.

Экспорт реализован с помощью Apache POI 5.4.1. Библиотека позволяет открывать существующий XLSX-шаблон из classpath (export-template.xlsx) и записывать значения в заданные ячейки, не разрушая стили и объединения. Альтернативы (генерация книги «с нуля», CSV-выгрузка) отклонены, поскольку не удовлетворяют требованию визуальной идентичности с утверждённым бланком.

Средства контроля качества включают JUnit и Spring Boot Test для API-тестов (DocumentControllerWebTest), а также специализированные тесты структуры экспорта (ExportTemplateStructureTest). OpenAPI (springdoc) применяется для синхронизации контракта API с документацией и фронтенд-клиентом.

## 3.2 Описание работы программы

Пользовательский сценарий начинается с открытия веб-приложения core-form-frontend. На шаге 1 мастера пользователь вводит общие данные: наименование и шифр ТРУ (в UI объединены в одно поле), этап выполнения, отчётный и плановый год. При нажатии «Сохранить черновик» frontend вызывает POST /api/v1/documents (для нового документа) или PATCH /api/v1/documents/{id}/common (для существующего). Backend сохраняет запись в таблицах document и document_common_info, возвращает UUID документа.

На шаге 2 пользователь выбирает раздел из справочника GET /api/v1/dictionaries. Интерфейс отображает вычисленные атрибуты: номер формы (4, 5 или 6), номер раздела, прогнозируемый rowNo. Пользователь заполняет поля col2–col10, col13_1, col13_2, col14, col15 в зависимости от типа формы. Поля col2, col14 и col15 реализованы с автодополнением: компонент AutocompleteInput выполняет отложенный запрос к /reference-data/materials/search или /reference-data/suppliers/search; при выборе подсказки связанные графы заполняются автоматически (коды материала или реквизиты поставщика). Кнопка «Справочники» открывает модальное окно ReferenceDataManager для прямого добавления, редактирования и удаления записей без прерывания работы с документом. Поля col11 и col12 отображаются как только для чтения: клиент может показывать предварительный расчёт, но итоговые значения фиксируются на сервере при POST или PATCH /entries; одновременно вызывается syncFromEntryFields для пополнения справочников.

Таблица введённых строк поддерживает фильтрацию по разделу, форме и статусу валидации. Доступны действия редактирования, дублирования и удаления. При удалении backend перенумеровывает оставшиеся строки раздела через EntryRowNumberService, сохраняя непрерывность нумерации.

Шаг 3 выполняет параллельные запросы GET /entries и GET /totals. UI отображает карточки агрегатов по каждой форме и список строк со статусом INVALID. Если preview не актуален (данные менялись после последнего просмотра), кнопка экспорта заблокирована. При подтверждении пользователь инициирует POST /documents/{id}/export с параметрами format=xlsx и mode=fill_template. Сервис XlsxTemplateExportService загружает шаблон, заполняет общий блок и строки согласно mapping-spec, возвращает массив байтов. Файл сохраняется во временное хранилище ExportFileStore и отдаётся клиенту через GET /files/{fileId}.

Обработка ошибок унифицирована: ApiExceptionHandler формирует конверт ErrorEnvelope с кодом VALIDATION_ERROR, NOT_FOUND, CONFLICT или INTERNAL_ERROR. Frontend отображает сообщения пользователю и подсвечивает проблемные поля, что сокращает время исправления данных перед повторным экспортом.

Реализация backend сосредоточена в классе DocumentApiService, который координирует транзакции, валидацию, расчёт computed-полей, синхронизацию справочников через ReferenceDataService и делегирует экспорт XlsxTemplateExportService. Контроллеры DocumentController и ReferenceDataController остаются тонким слоем маршрутизации без бизнес-логики. На frontend основная логика сосредоточена в App.tsx, включая управление шагами, dirty-state, блокировку beforeunload при несохранённых изменениях и интеграцию AutocompleteInput; компонент ReferenceDataManager инкапсулирует CRUD справочников.

## 3.3 Системные требования

Минимальные требования к серверу приложений: 64-разрядная ОС (Windows Server 2019+, Linux Ubuntu 22.04+), 2 ядра CPU, 4 ГБ RAM, 10 ГБ свободного дискового пространства (с учётом БД и временных файлов экспорта). Рекомендуется 4 ядра и 8 ГБ RAM при одновременной работе до 20 пользователей в учебно-опытной эксплуатации.

Требования к СУБД: PostgreSQL 15+, отдельный том для данных, резервное копирование по расписанию (pg_dump или снапшоты СХД). Кодировка UTF-8. Сетевой доступ к порту 5432 ограничивается подсетью приложения.

Требования к рабочему месту пользователя: современный браузер (Chromium 120+, Firefox 115+, Edge 120+), разрешение экрана не ниже 1366×768, постоянное сетевое соединение с сервером frontend. Клиентские вычислительные ресурсы минимальны, поскольку расчёты выполняются на сервере.

Программные зависимости backend: JDK 21, Maven 3.9+. Программные зависимости frontend: Node.js 20+, npm 10+. Для сборки backend используется команда mvn -q package, для запуска dev-режима frontend — npm run dev с проксированием API на localhost:8080.

Требования к развёртыванию MVP: переменные окружения для подключения к БД (DB_URL, DB_USER, DB_PASSWORD), путь к шаблону экспорта (app.export.template-path), настройка CORS при размещении frontend и backend на разных origin. Аутентификация в MVP не требуется; для промышленной эксплуатации рекомендуется дополнить контур SSO, журналированием действий и разграничением ролей «экономист / согласующий / администратор».

Требования к сопровождению: версионирование API (/api/v1), миграции Flyway при изменении схемы (включая V3 для справочников), регрессионные тесты экспорта при обновлении шаблона Excel. Документация API публикуется через Swagger UI (теги Document и Reference Data), пользовательские сценарии — в UI_SPEC.md и BPMN-project-processes.md.
