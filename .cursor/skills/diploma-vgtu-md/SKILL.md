# Diploma VGTU MD

## Назначение

Скилл задает единый рабочий стандарт для диплома ВГТУ на базе SplitM:
- постановка и сопровождение ТЗ в `.md`;
- структурирование диплома по обязательным разделам;
- поддержание стиля «студент-хорошист»;
- поэтапная подготовка текста к антиплагиату.

Это **source-of-truth** для профиля `diploma-vgtu` в `word-worker`.
При конфликтах правил применять приоритеты из `.cursor/skills/document-governance/SKILL.md`.

Базовая тема по умолчанию:
- «Приложение для учета общих расходов с друзьями, семьей или коллегами».

Для новых тем ВКР:
- перед началом генерации обновлять тему, объект, предмет и терминологию под текущую постановку;
- не фиксировать название приложения жестко, использовать актуальное имя проекта из постановки.

## Когда применять

Применять скилл, если пользователь просит:
- написать/обновить ТЗ диплома;
- составить план или каркас глав;
- подготовить markdown-черновики разделов диплома;
- описать современную методологию разработки для SplitM;
- повысить уникальность текста и подготовить к антиплагиату.

## Политика единообразия (всегда)

- При любых новых задачах по ВКР сначала сверяться с актуальными правилами ВГТУ и текущим скиллом.
- Если пользователь уточнил оформление, это уточнение сразу вносится в скилл до следующей генерации.
- Новые главы, пересборка глав и merge-версия всегда делаются в одном и том же формате оформления.
- Любые изменения в стиле/структуре сразу распространяются на все генераторы (`chapter`, `references`, `merge`), чтобы не возникало расхождений между файлами.

## Рабочая структура (текущий проект)

Для текущего процесса использовать структуру:
1. Введение
2. Глава 1. Анализ предметной области
3. Глава 2. Методы решения
4. Глава 3. Реализация
5. Заключение
6. Список литературы
7. Приложения (при наличии)

В текущем режиме НЕ включать:
- титульный лист;
- задание на ВКР;
- аннотацию ВКР.

Раздел `СОДЕРЖАНИЕ` формировать только при объединенной сборке всех глав (`merge`).
Важно: слово `СОДЕРЖАНИЕ` в документе должно быть только визуальным заголовком страницы оглавления и НЕ должно появляться отдельной строкой внутри самого оглавления (TOC).
Формат содержания в merge-версии фиксировать в виде:
- `ВВЕДЕНИЕ`
- `1 ...`, `1.1 ...`, `1.2 ...`
- `2 ...`, `2.1 ...`, `2.2 ...`
- `3 ...`, `3.1 ...`, `3.2 ...`
- `ЗАКЛЮЧЕНИЕ`
- `СПИСОК ЛИТЕРАТУРЫ`
с автоматическими номерами страниц (через поле TOC Word).

Разделы `Экономическая часть` и `Безопасность жизнедеятельности` не добавлять по умолчанию; включать только по прямому запросу.

Разделы `Термины и определения` и `Обозначения и сокращения` опциональны.

Ограничения по объему:
- общий объем не менее 45 страниц;
- ориентир: 3 главы по 15-20+ страниц каждая.

## Формат артефактов по главам

Для каждой главы диплома обязательно готовить два отдельных артефакта:
- отдельный файл Word (например, `Глава_1_Анализ.docx`, `Глава_2_Методы.docx`, `Глава_3_Реализация.docx`);
- отдельный Python-скрипт генерации этой главы (например, `build_chapter_1.py`, `build_chapter_2.py`, `build_chapter_3.py`).

Список литературы также оформляется как отдельный комплект артефактов:
- отдельный Word-файл (например, `Список_литературы.docx`);
- отдельный Python-скрипт генерации (например, `build_references.py`).

Требование процесса:
1. Сначала правится текстовая постановка и контент главы в Markdown.
2. Затем обновляется Python-код генерации конкретной главы.
3. После этого пересобирается только соответствующий `.docx`.
4. Для библиографии выполняется отдельный цикл генерации `build_references.py` -> `Список_литературы.docx`.
5. Для универсального CLI использовать `pycode/diploma_build.py`:
   - глава: `python pycode/diploma_build.py chapter --number 1`
   - литература: `python pycode/diploma_build.py references`
   - объединение: `python pycode/diploma_build.py merge`

Запрещено смешивать весь диплом в один генератор и один общий `.docx` на этапе черновой разработки глав.

## Таблицы и диаграммы

- Таблицы в итоговом `.docx` должны создаваться как настоящие Word-таблицы (`Table Grid`), а не как текст/markdown-таблицы.
- Для каждой главы обязательно добавлять визуальные материалы: минимум 2-3 диаграммы/схемы/скриншоты на главу.
- Диаграммы последовательности, архитектурные схемы и сравнительные графики должны генерироваться и вставляться в Word автоматически через Python.
- При доступности draw.io CLI предпочтительно генерировать схемы и часть сравнительных таблиц через draw.io с экспортом в PNG для вставки в Word.
- Все рисунки должны иметь подписи формата «Рисунок N. ...».
- Места для ручной вставки визуалов помечать отдельной строкой в формате: `(ВСТАВИТЬ СКРИНШОТ: НАЗВАНИЕ ЭКРАНА)` — обязательно в скобках, КАПСОМ.
- В итоговом Word такие плейсхолдеры должны быть красным текстом, чтобы их можно было быстро найти и заменить вручную без дополнительных правок текста.
- Под каждым красным плейсхолдером обязательно добавлять отдельную строку подписи вида: `Рисунок N. ...` (обычный черный текст), чтобы при ручной замене сохранялась готовая подпись иллюстрации.
- Для плейсхолдера с таблицей подпись формировать как `Таблица N. ...`.
- В главе анализа обязательно поддерживать таблицу сравнения минимум из 3 аналогов, один из которых — `Splitwise`.

## Стиль и тональность

- Язык: русский.
- Стиль: академичный и понятный, без избыточной наукообразности.
- Уровень подачи: «студент-хорошист».
- Логика абзацев: «проблема -> решение -> результат».
- Запрещено копировать готовые шаблонные куски без адаптации к текущей теме.
- В тексте диплома и артефактах использовать одно согласованное название проекта из постановки.
- Не использовать markdown-выделение вида `**...**` в основном тексте глав.
- Заголовки в итоговых Word-документах должны быть черного цвета.
- Не оставлять следов использования ИИ: в тексте не должно быть служебных фраз, самореференций, вопросов к читателю о дальнейшей генерации и иных метакомментариев.

## Обязательные требования ВГТУ (Пр 2.01.01-2020)

- Формат листа: А4, печать на одной стороне.
- Поля: левое 20 мм, правое 10 мм, верхнее 20 мм, нижнее 10 мм.
- Шрифт: Times New Roman, цвет черный.
- Основной текст: 14 pt.
- Заголовки и подзаголовки (включая структурные разделы): 16 pt, без жирного.
- Межстрочный интервал: 1.5; выравнивание по ширине; абзацный отступ 1.25 см.
- Нумерация страниц: сквозная, арабскими цифрами, внизу по центру, без точки; титульный лист учитывается, но номер на нем не ставится.
- Наименования структурных элементов (`СОДЕРЖАНИЕ`, `ВВЕДЕНИЕ`, `ЗАКЛЮЧЕНИЕ`, `СПИСОК ЛИТЕРАТУРЫ`, `ПРИЛОЖЕНИЕ`) — по центру, прописными буквами, без точки, с новой страницы.
- Разделы и подразделы основной части нумеруются; введение и заключение как разделы не нумеруются.
- Введение не должно быть оформлено как аннотация; не размещать таблицы и рисунки во введении.
- Все рисунки и таблицы должны иметь ссылки в тексте.
- Подписи рисунков: `Рисунок N – Наименование`.
- Подписи таблиц: `Таблица N – Наименование`.
- Ссылки на источники в тексте — в квадратных скобках в порядке появления.
- Список литературы формировать в порядке появления ссылок в тексте.

## Стандарт ТЗ в Markdown

При создании `ТЗ_диплом.md` включать минимум:
- цель и рамки диплома;
- требования к объему;
- детальный каркас разделов и подпунктов;
- требования к стилю и оформлению;
- принципы современной методологии разработки;
- цикл подготовки под антиплагиат;
- критерии приемки результата.

В ТЗ также фиксировать:
- схему файлов по главам (какой `.md`, какой `.py`, какой `.docx`);
- правила именования артефактов;
- порядок сборки глав по отдельности.
- обязательный комплект структурных элементов ВКР по Пр 2.01.01-2020;
- требования к полям, нумерации страниц, подписям таблиц/рисунков и ссылкам.

## Требования к списку литературы

Список источников должен быть реальным и проверяемым.

Обязательно:
- использовать только существующие публикации, стандарты и официальную документацию;
- проверять, что источник действительно доступен и относится к теме;
- включать профильные источники по стеку SplitM.

Минимальный состав источников:
- официальная документация Flutter;
- официальная документация Spring Boot;
- официальная документация Keycloak;
- официальная документация PostgreSQL;
- официальная документация Docker и Docker Compose;
- профильные книги/статьи по проектированию ИС и информационной безопасности.

Запрещено:
- пустые заглушки в библиографии;
- вымышленные названия публикаций;
- ссылки без выходных данных, если это не web-документация.

## Чеклист готовности главы

Перед завершением каждой главы проверить:
- [ ] Глава закрывает заявленные задачи раздела.
- [ ] Есть привязка к архитектуре и решениям SplitM.
- [ ] Использованы авторские формулировки и аналитические выводы.
- [ ] Добавлены элементы, повышающие уникальность (сравнения, таблицы, схемы, выводы).
- [ ] Сохранен единый терминологический стиль.
- [ ] Глава готова к итерации антиплагиат-доработки.

## Цикл антиплагиат-доработки

Для каждого крупного раздела применять процесс:
1. Сформировать тезисный план.
2. Написать авторский черновик на основе фактов проекта.
3. Провести редактуру и убрать шаблонные обороты.
4. Проверить уникальность.
5. Переписать проблемные фрагменты через углубление анализа.
6. Повторить шаги 3-5 до рабочего уровня уникальности.

## Шаблон стартовой постановки

```markdown
## 5. План написания по этапам
## 6. Цикл повышения уникальности
## 7. Критерии приемки
```
